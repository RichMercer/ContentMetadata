Why not extended attributes?

ContentMetadata was built to replace extended attributes for developers who used them to store their own data. Extended attributes:

  • aren't available on every entity, for example wikis and comments;
  • can hurt performance when a lot of data is stored against one object;
  • can't be used to look content up, because the APIs don't filter on them;
  • are readable by anyone who can read the entity, and editable by anyone who can edit it.

ContentMetadata keeps its data in its own table, separate from the entity, and you choose which APIs can reach it. It does not check permissions on the content itself, so read Security before exposing it to users.

Install

Step 1 of 3

Add the package, deploy ContentMetadata.dll with your other plugins, then enable ContentMetadata Plugin in Administration. On install, the plugin creates its Metadata table in its own SQL Server schema.

Shell

dotnet add package TelligentContentMetadata
PackageVerint Community.NET
14.x14.NET 10

The plugin has one option, Enable search (off by default), which adds metadata to the search index. See Search.

Database access

Step 2 of 3

Verint Community 14 no longer lets plugins use the Community database directly. ContentMetadata implements ISqlServerConnectedPlugin, so the platform supplies a connection string that can only reach the plugin's own schema.

Verint hosted

Nothing to configure. The schema and connection string are created for you.

Self-hosted

Create a SQL Server login and user for the plugin. Give the user its own default schema, owned by that user, and CREATE TABLE permission. Then add the connection string to PluginConnectionStrings in your environment configuration ↗. Without it, the platform won't initialise the plugin.

settings.json

"PluginConnectionStrings": {
  "ContentMetadata.Plugins.ContentMetadataPlugin, ContentMetadata": "server=...;database=...;uid=contentmetadata;pwd=...;TrustServerCertificate=True"
}

SQL · self-hosted setup

CREATE LOGIN [contentmetadata] WITH PASSWORD = N'<strong password>';
GO
USE [community_app];
GO
CREATE USER [contentmetadata] FOR LOGIN [contentmetadata] WITH DEFAULT_SCHEMA = [contentmetadata];
GO
CREATE SCHEMA [contentmetadata] AUTHORIZATION [contentmetadata];
GO
GRANT CREATE TABLE TO [contentmetadata];

Upgrading from 1.x

Step 3 of 3

Earlier versions stored metadata in [dbo].[custom_Metadata] with stored procedures in dbo. Nothing reads or writes dbo at runtime any more; the plugin only touches it during install to migrate your data. Each time the plugin installs, it:

  1. copies every legacy row into [<plugin schema>].[Metadata], skipping rows that are already there;
  2. checks that every legacy row is present in the plugin schema;
  3. removes the legacy table and the custom_Metadata_* procedures, but only if step 2 succeeded. Otherwise the table is kept and event 3662 is logged.

The migration is safe to repeat. Back up the database before upgrading.

Self-hosted sites

The platform's read access to dbo during install only exists in Verint's hosted environment. Before you deploy 14.x, grant the plugin's user read access to the legacy table. Install only runs when the plugin version changes, so make the grant first. The grant is removed along with the table once the data is migrated.

SQL

GRANT SELECT ON [dbo].[custom_Metadata] TO [contentmetadata];

Usage

The in-process, widget and REST APIs share one implementation, so they behave the same. Each lists, gets, sets and deletes metadata for an IContent entity, and can find content by key and value. You always pass the ContentId of the content the metadata belongs to.

  • Keys are 1 to 64 characters and compared exactly, so Colour and colour are different keys.
  • Values are strings of any length. Setting an empty value deletes the key.
  • When content is deleted, its metadata is deleted too.
  • Reads are cached for 100 seconds per content item. A change clears the cache on the server that made it; other servers may return the old value until their cache expires.

In-process API

Use IContentMetadataApi from C# in plugins or other custom code.

C#

var api = Apis.Get<IContentMetadataApi>();

// All metadata for a piece of content
IReadOnlyList<ContentMetadata> items = api.List(contentId);

// One value. Returns an empty ContentMetadata (Value is null) when the key isn't set.
ContentMetadata item = api.Get(contentId, "MyKey");
bool featured = item.GetBoolValue(false);
int priority = item.GetIntValue(0);

// Add or update a value
api.Set(contentId, contentTypeId, "MyKey", "MyValue");

// Delete one key, or every key for the content
api.Delete(contentId, "MyKey");
api.Delete(contentId);

// Find content by metadata: every match, or the first of one content type
IReadOnlyList<ContentMetadata> matches = api.List("MyKey", "MyValue");
ContentMetadata match = api.Get(contentTypeId, "MyKey", "MyValue");

ContentMetadata.Extensions adds the same operations to IContent:

C#

using ContentMetadata.Extensions;

var all = post.GetMetadata();
string value = post.GetMetadata("MyKey");
int count = post.GetMetadataInt("Count", 0);
bool enabled = post.GetMetadataBool("Enabled", false);
post.SetMetadata("MyKey", "MyValue");

Widget API

The $metadata_v1_content Velocity extension exposes the same methods to widgets. Encode values before output, and check the accessing user's permissions before calling Set or Delete from a callback.

Velocity

#set($items = $metadata_v1_content.List($contentId))
#set($item = $metadata_v1_content.Get($contentId, 'MyKey'))
$core_v2_encoding.HtmlEncode($item.Value)

#set($item = $metadata_v1_content.Set($contentId, $contentTypeId, 'MyKey', 'MyValue'))
$metadata_v1_content.Delete($contentId, 'MyKey')  ## Delete one key
$metadata_v1_content.Delete($contentId)           ## Delete every key

#set($matches = $metadata_v1_content.List('MyKey', 'MyValue'))

REST API

Endpoints are under /api.ashx/v2/; add .json or .xml to choose the format. Each response has Data and Errors. Parameters go in the query string or, for POST and DELETE, in form fields.

EndpointParametersReturns
GET metadata/{ContentId}Key (optional)Every item for the content, or the one item for Key
GET findmetadata/{Key}Value (required), ContentTypeId (optional)Every item with that key and value, or the first of that content type
POST metadataContentId, ContentTypeId, Key, ValueThe saved item
DELETE metadataContentId, KeyNothing

Shell

curl -H "Rest-User-Token: <token>" \
  "https://community.example.com/api.ashx/v2/metadata/<ContentId>.json?Key=MyKey"

Scopes

Verint Community 14 only lets a caller use endpoints whose scopes it has been granted. These endpoints are in the Content Metadata scope group: contentmetadata.metadata.readonly for GET and the matching modify scope for POST and DELETE. Grant them only to the API keys, OAuth clients and widgets that need them.

Search

With Enable search on, metadata is added to each item as it is indexed. The field name is the key in lowercase with a metadata_ prefix, so MyData becomes metadata_mydata, and you can query it through the standard search APIs:

SearchResults query

query=metadata_mydata:myvalue

Solr field names and values are case sensitive. Use keys made of letters, digits and underscores, and don't enable search if any metadata is sensitive.

Security

Read before exposing the APIs

ContentMetadata does not check whether the caller can see or edit the content that a ContentId points to.

  • REST: the read scope allows reading metadata for any content ID, including content in private groups, and findmetadata can reveal which content IDs hold a value. The modify scope allows changing or deleting metadata on any content. Grant these scopes only to trusted callers, and don't store anything sensitive if untrusted users can reach the endpoints.
  • Widgets and plugins: your code decides who can do what. Before calling Set or Delete with an ID from the request, check that the accessing user may edit that content. HTML-encode values before rendering them.
  • Content type: ContentTypeId is stored as supplied and isn't checked against the content, so don't rely on it alone.
  • Search: indexed metadata can be searched by anyone who can see the content.

Please report vulnerabilities privately through GitHub security advisories ↗, not in a public issue.

Event log

The plugin writes to the Community event log with the category ContentMetadata.

EventTypeMeaning
3661ErrorNo SQL Server connection was provided, so the table wasn't created. Add the PluginConnectionStrings entry.
3662ErrorLegacy rows were copied but some couldn't be verified. The legacy table was kept.
3663InformationLegacy data was migrated, and the legacy table and procedures were removed.
3664InformationNo legacy table was visible during install.
3665ErrorA REST request failed unexpectedly. The caller gets a generic error; the details are here.

Supported entities

Any entity that implements IContent. Commonly used ones include Achievement, Blog, BlogPost, Calendar, Event, Challenge, Idea, Comment, ContentPage, Conversation, ConversationMessage, Forum, ForumThread, ForumReply, Gallery, Media, Group, GroupUser, KnowledgeCollection, Document, Leaderboard, StatusMessage, User, Wiki and WikiPage.
